## Deletion rule implemented

1. Parse the `accountId` path parameter as a UUID (handler-level validation returns 400 on invalid input).
2. Start a transaction, select the Account with `isNull(deletedAt)` and `FOR UPDATE`.
3. If the Account is missing or soft-deleted, throw `AccountNotFoundError` → 404.
4. Select all Account Capacities with `FOR UPDATE`.
5. If any Capacity exists, check whether any `capacity_customers` row references one of those Capacities (regardless of status or `deletedAt`).
6. If assignment history exists, throw `AccountHasAssignmentHistoryError` → 409 and rollback.
7. Otherwise, explicitly delete `account_backup_codes`, then `account_capacities`, then the `accounts` row, and commit.
8. Return 204 No Content.

Because all child foreign keys are `ON DELETE NO ACTION`, the service deletes children explicitly in the correct order. The `FOR UPDATE` locks on the Account and Capacities serialize any concurrent `capacity_customers` INSERT; once the Capacities are deleted, the FK check fails and the assignment cannot be created.

## Race-safety mechanism

A deterministic trigger-based test demonstrates that deletion cannot race successfully against assignment creation:

- A `BEFORE DELETE` trigger on `account_capacities` sleeps for 300 ms while the delete transaction holds the row locks.
- While the trigger is running, a concurrent `capacity_customers` INSERT is attempted.
- The INSERT is serialized behind the delete transaction's locks; after the Account and Capacities are deleted, the INSERT fails the foreign-key constraint.
- The test verifies the delete returns 204 and the assignment insert fails.
